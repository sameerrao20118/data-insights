# Evaluator-only holdout (seed 1337)

Generated by the same `generate_data.py` used for the main dev dataset in
`data_generator/output/`, but with `--seed 1337` instead of the default 42
— different realized clients, transactions, and trigger events, same
generation logic.

**What this does and doesn't fix.** This gives you a second, independently
sampled dataset with its own `protected_evaluator_only/trigger_events.csv`,
so a final evaluation run doesn't reuse the exact same rows the detector
was tuned against. What it does NOT fix: this coding session still
authored and knows the injection logic (windows, multipliers, thresholds)
for every trigger type, in both datasets. A detector rule shaped by that
knowledge — even unconsciously, even when "validated" against this holdout
— is not evidence of genuine detection ability the way a rule built by
someone with zero visibility into the generator would be.

For a real holdout guarantee, generate a third dataset with a seed and
minor generation-logic tweaks chosen by someone who does not share this
session's context, and never surface its `trigger_events.csv` (or metrics
derived from repeatedly probing it) back into this session.

Layout mirrors `data_generator/output/`: source tables (clients, accounts,
transactions, facilities, balances, risk_ratings, entity_groups,
crm_interactions) sit here for the detector to read; `trigger_events.csv`
sits under `protected_evaluator_only/` for the evaluator only.
