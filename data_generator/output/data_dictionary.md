# Data Dictionary — Synthetic Commercial/Institutional Banking Dataset

Generated by `data_generator/generate_data.py`. **Fully synthetic** — no real
client, account, or transaction data. Loosely calibrated to public aggregate
statistics (ECB SAFE survey on SME finance, Eurostat structural business
statistics, ECB payments statistics), not fitted to any real client-level
records.

Regenerate with a fixed seed (42) for reproducibility, or change `SEED` /
`N_CLIENTS` / date range at the top of the script for a different run.

## clients.csv (300 rows)

| column | type | description |
|---|---|---|
| client_id | string | Unique client identifier, `CL#####` |
| legal_name | string | Synthetic company name |
| segment | enum | SME / Mid-Corporate / Large-Corporate / Institutional |
| sector | string | Broad industry sector |
| nace_section | string | NACE Rev. 2 section letter (broad grouping) |
| country | string | ISO country code (EU country) |
| currency_home | string | Client's home settlement currency |
| annual_revenue_eur_est | float | Estimated annual revenue, EUR |
| onboarding_date | date | Date the client relationship began |
| relationship_manager_id | string | Assigned RM, `RM###` |
| seasonality_pattern | enum | Cash-flow seasonality shape applied to this client's sector (summer_peak / harvest_peak / q4_peak / winter_peak / none) |

## accounts.csv (~540 rows)

| column | type | description |
|---|---|---|
| account_id | string | `{client_id}-A{n}` |
| client_id | string | FK to clients |
| currency | string | Account currency |
| account_type | enum | current / savings / credit_facility |
| is_primary | bool | True for the client's main operating account |
| credit_limit | float | Only set for credit_facility accounts |
| open_date | date | = client onboarding_date |

## transactions.csv (~297k rows)

| column | type | description |
|---|---|---|
| transaction_id | string (UUID) | Unique transaction id |
| account_id | string | FK to accounts |
| client_id | string | FK to clients (denormalized for convenience) |
| date | date | Transaction date |
| amount | float | Signed amount (positive = credit/inflow, negative = debit/outflow) |
| currency | string | Transaction currency (may differ from client home currency — see FX_EXPOSURE_NEW trigger) |
| direction | enum | credit / debit |
| category | string | supplier_payment, payroll, tax_payment, rent_lease, loan_repayment, utilities, professional_fees, fx_payment, customer_receipt, contract_payment, grant_subsidy, loan_disbursement, interest_income, refund |
| counterparty_id | string | Synthetic counterparty reference (stable per client, so recurring vs. new counterparties are distinguishable) |
| channel | string | SEPA_CREDIT_TRANSFER / SWIFT / CARD / DIRECT_DEBIT / INTERNAL |
| balance_after | float | Running primary-account balance after this transaction (approximate — credit facility draws are logged separately) |

## trigger_events.csv (~220 rows) — GROUND TRUTH, held out from transactions.csv

This is the answer key. Each row is a trigger event deliberately embedded into
a client's transaction history. **Do not feed this file into a rule-engine or
model as a feature** — use it only to score precision/recall of whatever
detector you build against transactions.csv. About 55% of clients have 1-2
embedded trigger events; the rest have none (pure noise / baseline behavior),
which matters for measuring false-positive rate.

| column | type | description |
|---|---|---|
| client_id | string | FK to clients |
| trigger_type | enum | see below |
| event_date | date | Approximate date the underlying pattern shift begins |
| account_id | string | Primary account where the pattern is expressed |

### Trigger types and their commercial-banking rationale

| trigger_type | what's embedded in the data | typical NBA product angle |
|---|---|---|
| TENDER_PAYMENT | A single large inbound payment, well above the client's historical transaction size, inconsistent with normal receivables pattern | Short-term deposit sweep, trade finance, working capital facility |
| CASHFLOW_STRESS | ~30-75 day window of reduced/volatile inflows and thinner outflows (proxy for margin squeeze) | Overdraft/credit line, invoice financing, advisory outreach |
| FX_EXPOSURE_NEW | First-time appearance of a foreign currency (USD/GBP/CHF/JPY) in the client's transaction stream | FX hedging, multi-currency account, trade finance |
| TREASURY_SURPLUS | Sustained window of idle-cash buildup on the primary account | Term deposit, money market fund, cash sweep product |
| NEW_COUNTERPARTY_CONCENTRATION | A new, unusually large counterparty appears and recurs | New receivables/payables relationship — cash management, collections products |
| CREDIT_UTILIZATION_SPIKE | Increased drawdown on an existing credit_facility account (only possible for clients that hold one) | Facility limit review, restructuring, additional credit line |
| DORMANT_REACTIVATION | 60-150 day near-silent window followed by activity resuming | Re-engagement outreach, relationship review |
| RECURRING_REVENUE_ESTABLISHED | A new regular recurring inflow pattern begins mid-history | Cash management / collections product, potential lending base expansion |

## Known limitations (v1)

- `CREDIT_UTILIZATION_SPIKE` is underrepresented (few embedded events) because
  only clients holding a `credit_facility` account are eligible — by design,
  since not all clients hold one, but worth knowing before drawing conclusions
  about detector recall on this trigger type specifically.
- Counterparty identifiers are synthetic tokens, not real business names —
  fine for pattern-detection prototyping, not for anything requiring realistic
  entity resolution.
- No multi-client counterparty overlap (i.e., no shared real-world suppliers
  across different clients) — each client's counterparty universe is private
  to them.
