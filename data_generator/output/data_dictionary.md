# Data Dictionary — Synthetic Commercial/Institutional Banking Dataset

Generated by `data_generator/generate_data.py`. **Fully synthetic** — no real
client, account, or transaction data, and no raw records copied from any
dataset below. The *relational structure* and the *format* of certain
fields are modeled on real, publicly documented references so the schema
resembles what a commercial/institutional banking analytics division
actually works with, instead of one flat table:

| Reference | What it's real | What it informed here |
|---|---|---|
| **Berka / PKDD'99 "Financial Dataset"** (1999 Discovery Challenge) | Real, anonymized Czech retail-bank data; canonical academic relational-banking benchmark (CTU Prague Relational Learning Repository, widely used in university data-mining courses) | Normalizing client / account / facility / transaction as separate linked entities instead of one flat table |
| **Lending Club public loan-level dataset** | Real, publicly released loan performance data; heavily used in academic credit-risk/ML research | `facilities.csv` structure — amount, term, rate, purpose, status, grade-like risk linkage |
| **UCI Statlog (German Credit Data)** | Real, canonical academic credit-risk classification dataset | `risk_ratings.csv` masterscale structure (ordinal grade + PD) |
| **PaySim** (Lopez-Rojas et al. 2016) | Synthetic-but-validated mobile-money methodology, widely used in academic fraud-detection research | Balance-before/after convention, counterparty tokenization |
| **ISO 20022 External Purpose Codes** | Real global payments-messaging standard | `iso20022_purpose_code` on transactions |
| **Booking date vs. value date** | Real settlement convention used by every core-banking/payments system | `booking_date` / `value_date` split on transactions |
| **IBAN — ISO 7064 MOD 97-10 checksum** | Real algorithm | IBANs here are *structurally valid* (correct length, correct check digits) but are **not registered real account numbers** |
| **LEI — ISO 17442** | Real global legal-entity identifier standard (GLEIF) | LEIs here are *structurally valid* (correct length, correct check digits per the same MOD 97-10 algorithm) but are **not GLEIF-registered** |
| **Eurostat NACE Rev. 2** | Real EU industry classification | `nace_code` uses real 4-digit codes, not placeholders |

Distributional choices (revenue bands, seasonality, SME credit-line
prevalence, group-structure prevalence, LEI adoption rate by segment) are
loosely calibrated to public aggregate statistics (ECB SAFE survey on SME
finance, Eurostat structural business statistics, ECB payments statistics,
GLEIF's published LEI-holder composition) — not fitted to real client-level
data, which does not exist for us to see.

Regenerate with a fixed seed (42) for reproducibility, or change `SEED` /
`N_CLIENTS` / date range at the top of the script for a different run.

## entity_groups.csv (~18 rows)

Corporate/institutional group hierarchy. In real commercial/institutional
banking, NBA and credit decisions are usually made at **group** level, not
single-legal-entity level — this table is what makes that possible.

| column | type | description |
|---|---|---|
| group_id | string | `GRP####` |
| group_name | string | Synthetic group name |
| ultimate_parent_client_id | string | FK to clients — the group's top entity |
| ultimate_parent_country | string | Country of the ultimate parent |
| group_type | enum | corporate_group / institutional_consolidation |
| member_count | int | Number of clients in the group |

| column | type | description |
|---|---|---|

| segment | enum | SME / Mid-Corporate / Large-Corporate / Institutional |
| sector | string | Broad industry sector |
| nace_section | string | NACE Rev. 2 section letter |

| country | string | ISO country code (EU country) |

| onboarding_date | date | Date the client relationship began |
| relationship_manager_id | string | Assigned RM, `RM###` |

## risk_ratings.csv (~783 rows) — internal credit rating history

Annual review cadence (31 March each year the client is active). Masterscale
structure modeled on academic credit-risk dataset conventions (UCI German
Credit / Lending Club "grade"). **Did not exist in v1** — no real bank runs
commercial NBA without a credit-risk gate on the recommendation.

| column | type | description |
|---|---|---|
| rating_id | string | `RTG######` |
| client_id | string | FK to clients |
| rating_date | date | Annual review date |
| internal_rating_grade | int 1-10 | 1 = best (~investment grade), 10 = default-adjacent |
| pd_1y_pct | float | 1-year probability-of-default estimate, looked up from grade |
| watchlist_flag | bool | True more often at grade ≥ 8 |

Clients that received a `CASHFLOW_STRESS` trigger event are downgraded in
their next annual review after the event — the rating table is causally
linked to transaction behavior, not independently random.

## crm_interactions.csv (~315 rows) — RM/campaign engagement log

The source of "did this trigger convert" labels an ML scoring model needs.
**Did not exist in v1** — without it there was no honest way to generate
training labels from data alone; ~75% of trigger events get a follow-up
interaction 3-25 days later, plus baseline routine relationship-management
noise unrelated to any trigger (to keep the label distribution realistic
rather than trigger-only).

| column | type | description |
|---|---|---|
| interaction_id | string | `INT######` |
| client_id | string | FK to clients |
| date | date | |
| channel | enum | RM_call, branch_meeting, email_campaign, digital_portal_offer |
| campaign_id | string | `CMP-{year}-{offer_type}` |
| offer_type | string | Product angle mapped from the trigger type (or generic_relationship_review for baseline noise) |
| linked_trigger_type | string, nullable | Blank for baseline noise interactions |
| outcome | enum | accepted / declined / no_response / pending |

## trigger_events.csv (~220 rows) — GROUND TRUTH, held out from transactions.csv

The answer key. Each row is a trigger event deliberately embedded into a
client's transaction history. **Do not feed this file into a rule-engine or
model as a feature** — use it only to score precision/recall of whatever
detector you build against transactions.csv (and now facilities/balances).
About 55% of clients have 1-2 embedded trigger events; the rest have none
(pure noise/baseline behavior), which matters for measuring false-positive
rate.

| column | type | description |
|---|---|---|
| client_id | string | FK to clients |
| trigger_type | enum | see below |
| event_date | date | Approximate date the underlying pattern shift begins |
| account_id | string | Primary account where the pattern is expressed |

### Trigger types and their commercial-banking rationale

| trigger_type | what's embedded in the data | typical NBA product angle |
|---|---|---|
| TENDER_PAYMENT | A single large inbound payment, well above the client's historical transaction size | Short-term deposit sweep, trade finance, working capital facility |
| CASHFLOW_STRESS | ~30-75 day window of reduced/volatile inflows and thinner outflows; also drives a rating downgrade in risk_ratings.csv | Overdraft/credit line, invoice financing, advisory outreach |
| FX_EXPOSURE_NEW | First-time appearance of a foreign currency (USD/GBP/CHF/JPY) | FX hedging, multi-currency account, trade finance |
| TREASURY_SURPLUS | Sustained idle-cash buildup on the primary account | Term deposit, money market fund, cash sweep product |
| NEW_COUNTERPARTY_CONCENTRATION | A new, unusually large counterparty appears and recurs | New receivables/payables relationship — cash management, collections products |
| CREDIT_UTILIZATION_SPIKE | Increased drawdown, now linked to a real facility record in facilities.csv | Facility limit review, restructuring, additional credit line |
| DORMANT_REACTIVATION | 60-150 day near-silent window followed by activity resuming | Re-engagement outreach, relationship review |
| RECURRING_REVENUE_ESTABLISHED | A new regular recurring inflow pattern begins mid-history | Cash management / collections product |

## Known limitations (v2)

- `CREDIT_UTILIZATION_SPIKE` is still somewhat underrepresented — only
  clients holding a credit_facility account are eligible.
- No transaction-level fee/charge line items, no full ISO 20022 message
  envelope (only the purpose code is modeled).
- `account_status` is always "active" — no closures/reactivations modeled
  at the account level (only at the trigger/dormancy level).
- Group hierarchy is single-level (parent + subsidiaries) — no multi-tier
  holding structures.
- No sanctions/AML watchlist or graph-based counterparty-network data
  (Elliptic/IBM-AML-style academic datasets would be the reference for
  that, if that becomes the next need).
